# AI 掼蛋游戏平台开发计划（v0.1）

**定位**：这是项目从当前原型推进到可玩、可评估 AI 平台的执行基线。本文不定义顺子、连对、钢板、炸弹及百搭缺口算法；这些另立规则专题后再纳入引擎。

## 1. 目标、边界与成功标准

### 1.1 产品目标

1. 提供一套确定、可测试、可回放的固定规则掼蛋引擎。
2. 支持四人两队的人类、规则 AI、搜索 AI 和学习型 AI 混合对局。
3. 在不泄漏隐藏手牌的前提下，为 Agent 提供稳定的观测与动作接口。
4. 将在线对局、离线训练、策略评测彻底分开，以便独立演进和扩容。

### 1.2 当前范围外

- 地方规则配置与多规则房间。
- 多组合甩牌。
- 顺子、连对、钢板、炸弹和同花顺的完整识别实现与优化。
- 真正的强化学习训练、账户体系、付费与公开上线。

### 1.3 分阶段验收原则

每个阶段须同时满足：功能可演示、自动测试通过、关键状态可复现、失败有明确错误原因。不要以“能跑一次”作为完成标准。

## 2. 现状审阅与优先问题

### 2.1 已具备的基础

- 基本数据模型、单张/对子/三张及部分终局、进贡与还贡规则。
- `Agent -> Action` 的抽象以及最小规则 Agent。
- 单局调度循环，能够以单张策略完成一局流程。
- LLM Agent 的响应解析、失败回退和基础测试。

### 2.2 P0：必须在继续功能开发前修复

| 问题 | 证据/影响 | 完成标准 |
|---|---|---|
| 牌组数量不正确 | 当前 `build_deck()` 只生成 100 张，`deal_hands()` 得到 `[27, 27, 27, 19]`；与两副 54 张和四人各 27 张矛盾 | 两副牌严格 108 张，四手均为 27 张；加入牌组组成、重复牌数量和发牌不变量测试 |
| 点数 2 的规则与牌组不一致 | `Rank.TWO` 已存在并被用作级牌，但发牌牌组没有普通 2 | 将“2 是否为正常点数、何时成为级牌、级牌轮转”写成唯一规则来源，并让牌组和排序按该来源实现 |
| 文档与工程结构漂移 | 纪要描述 `docs/rules_design.md` 和 7 项测试；实际规则文档在根目录，测试与模块已扩展 | 选定目录规范，更新 README、规则文档、测试说明；移除或标明重复的根目录原型文件 |
| 规则完成度被高估 | 牌型识别中仍有 `NotImplementedError`，当前完整对局仅依赖单张策略 | README 明确标注“单张 MVP”；完整规则验收必须以合法动作和规则测试为准 |

### 2.3 P1：在 Web/UI 前补齐

- 明确一盘比赛的起始级别、升级上限、最终获胜条件，以及局与盘的关系。
- 定义首局首出者、进贡后完整的换牌顺序与手牌变更；进贡测试须验证牌真实从给贡者移除、加入接收者并完成还贡。
- 为每次出牌定义机器可读的拒绝原因，例如 `NOT_IN_HAND`、`INVALID_CARD_TYPE`、`CANNOT_PASS_WHEN_LEADING`、`DOES_NOT_BEAT_LAST_PLAY`。
- 为随机数种子、规则版本、策略版本和完整动作序列建立可重放记录。

## 3. 建议的领域模型

### 3.1 单一权威状态

`GameState` 只能由规则引擎修改，至少包含：

- `rule_version`、`game_id`、`round_id`、随机种子、级牌、轮次与阶段。
- 座位、队伍、各玩家私有手牌、已出完顺序。
- 当前领出牌型、当前领出者、连续过牌人数、当前行动者。
- 进贡/还贡待办及已完成映射。
- 仅追加的事件列表或事件存储引用。

调度器、UI、Agent 都不得直接修改手牌或回合状态；它们只提交动作，规则引擎返回结果。

### 3.2 动作与事件

建议将命令和事件分开：

| 类型 | 例子 | 用途 |
|---|---|---|
| Command | `PlayCards`、`Pass`、`GiveTribute`、`ReturnTribute`、`Timeout` | 外部提出的意图，可能被拒绝 |
| Domain Event | `CardsPlayed`、`PlayerPassed`、`TrickReclaimed`、`PlayerFinished`、`RoundFinished` | 已发生的不可变事实，用于回放和统计 |
| View | `Observation`、`PublicGameView`、`PlayerGameView` | 按权限裁剪后的状态，绝不含其他玩家手牌 |

所有动作应含 `actor_id`、`expected_turn` 或状态版本、时间戳和可选 `request_id`，以避免断线重发造成重复出牌。

### 3.3 引擎 API

建议优先形成一个纯函数式边界：

```text
validate(state, command) -> ValidationResult
apply(state, command) -> (next_state, events)
observation_for(state, player_id) -> Observation
legal_actions_for(state, player_id) -> LegalActionSummary
```

初期 `legal_actions_for` 可只返回可过牌与候选动作摘要；后续再扩展为完整合法动作生成器，供搜索/RL 使用。验证和执行必须共享同一逻辑，不能由 UI 或 Agent 自己解释规则。

## 4. 模块边界与目录建议

```text
guandan_ai/
├── game_engine/        # 纯规则、状态、动作、事件、合法性与回放
├── agents/             # Agent 接口、规则 Agent、搜索/RL/LLM 适配器
├── match_runner/       # 本地模拟、比赛编排、超时策略；不承载规则
├── services/           # 未来 HTTP/WebSocket 房间服务
├── ui/                 # 未来 Web 前端
├── training/           # 离线环境、数据集、训练与评测
├── tests/
│   ├── unit/           # 每条规则和边界条件
│   ├── integration/    # 完整局、进贡、断线和超时
│   └── fixtures/       # 固定牌局、回放样本与反例
├── docs/
│   ├── rules/          # 唯一权威规则文本与待决策清单
│   ├── adr/            # 架构决策记录
│   └── development_plan.md
└── pyproject.toml
```

建议保留一个“规则版本”常量，并让每份牌谱与测试夹具携带该版本。即使当前不支持规则可配置化，版本号也能防止规则改动后旧回放被静默误读。

## 5. 分阶段路线图

### Milestone A：规则内核可信（当前优先）

**目标**：任何给定牌局和动作序列都能得到确定、可验证的结果。

- 修复 108 张牌和均分发牌不变量。
- 建立 `GameState / Command / Event` 最小模型，令 Match Runner 调用引擎而非直接改列表。
- 完成单张、对子、三张、过牌、收回出牌权、玩家出完和终局的端到端规则测试。
- 将进贡/还贡从“选择结果”扩展为真实状态迁移。
- 加入固定种子重放测试：同一牌局、同一动作序列应产生完全相同事件序列。

**验收**：100 个固定种子单张策略对局全部结束；每局 108 张牌守恒；无玩家手牌为负、无重复出牌、无越权状态访问。

### Milestone B：完整牌型规则（下次专题）

**目标**：完成顺子、连对、钢板、炸弹、同花顺及红心级牌缺口规则。

- 先锁定可读规则样例与反例，再实现识别和比较。
- 建立基于表格的牌型测试集，覆盖天然牌、1/2 张百搭、重复点数、非法输入与炸弹跨层比较。
- 属性测试：识别成功的牌型必须可比较；非法组合不得被接受；任意合法行动不会破坏牌数守恒。

**验收**：每个规则条目均有正例、反例和边界例；随机生成牌组的回归测试稳定通过。

### Milestone C：可玩本地 Demo

**目标**：一名人类与三名规则 AI 可完成一盘。

- 后端提供创建房间、加入座位、提交动作、获取私有观察、拉取事件五类最小接口。
- Web UI 仅展示当前玩家有权看到的信息；服务端再校验所有动作。
- 处理行动超时、刷新恢复、重复请求和最小对局日志。

**验收**：浏览器刷新后能从事件恢复；客户端无法从接口得到他人手牌；错误动作有可展示错误码。

### Milestone D：策略评测与搜索 AI

**目标**：可比较规则 Agent、随机 Agent 和搜索 Agent。

- 制定 `Agent` 时间预算、随机种子、异常/超时回退和版本元数据。
- 建立锦标赛运行器，输出胜率、置信区间、ELO、平均决策时延、非法动作率和未完成局率。
- 为 ISMCTS 实现 determinization、信息集输入和可取消的决策预算。

**验收**：固定策略集合可重复跑比赛；报告可追溯至每局回放和策略版本。

### Milestone E：训练、协作与平台化

**目标**：在可信引擎之上迭代学习型 AI 和多人体验。

- 构建 Gym 风格环境：`reset(seed)`、`observe(player)`、`step(command)`、奖励与终局信息。
- 训练/评估环境与线上服务分离；模型有数据版本、训练配置和评测基线。
- “信号牌”只通过公开动作历史学习，不新增私密通信通道；用对照实验衡量协作收益。
- 后续再增加观战、回放、统计、房间管理和性能优化。

## 6. 测试与质量门禁

### 6.1 必备测试层次

1. **单元测试**：牌、牌型、比较、进贡、状态迁移和错误码。
2. **集成测试**：固定牌局完整跑局、进贡后开局、超时、断线重连、混合 Agent。
3. **性质测试**：108 张守恒、牌不重复、手牌总数与已出牌总数守恒、所有事件可重放。
4. **回归夹具**：每个已修复 bug 留下一局最小可复现牌局。
5. **策略评测**：固定种子和时间预算，避免把随机波动误判为策略提升。

### 6.2 工程门禁

- 格式化、静态检查、类型检查和完整测试在提交前执行。
- 所有规则修复必须同时更新规则文本、测试和变更记录。
- 引入外部依赖前记录用途、许可证、版本锁定和离线开发方案。
- 不将 `.venv`、`__pycache__`、密钥或真实用户牌谱提交到版本库。

## 7. 架构决策清单（ADR）

每项决策单独记录背景、选择、替代方案、后果和日期。近期建议优先记录：

1. 固定规则版本及其权威文档位置。
2. 级牌、升级上限与整盘获胜条件。
3. 游戏状态是否采用事件溯源，以及回放 JSON 格式。
4. Agent 的超时、异常和非法动作处理策略。
5. 随机数与可重复性的规范。
6. 在线服务的认证、座位授权、隐藏信息与日志脱敏策略。
